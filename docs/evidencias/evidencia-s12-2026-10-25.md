## 1. Estrategia y alcance comprobable

CampusMarket opera como monolito modular FastAPI con MySQL: Publicaciones es propietario de `publicaciones` y `publicacion_imagenes`, Usuarios de sus identidades y sesiones y Administración de `reportes_publicacion`. Catálogo utiliza `backend/app/publicaciones/service.py` (no una proyección con eventos). MySQL es fuente de verdad. No se añade broker ni caché distribuida al MVP.

**No confundir:** transacción SQL local, lectura del autor tras escritura, idempotencia HTTP y atomicidad SQL+archivos son propiedades diferentes. El diseño separa garantías actuales de objetivos futuros.

## 2. Tabla operación → garantía de consistencia

| Operación real | Garantía observada o escogida | Si el dato llega tarde / riesgo | Mecanismo, ruta y límite |
|---|---|---|---|
| Crear publicación `POST /publicaciones` | Confirmación de escritura SQL local antes de responder; lectura posterior desde fuente, no desde proyección | El cliente puede recibir timeout aunque el commit ocurriera; repetir POST puede crear duplicados | `backend/app/publicaciones/repository.py:create_publication` ejecuta INSERT y `connection.commit()`; idempotencia del POST **pendiente**, registrada en S11 |
| Editar publicación | Escritura SQL local confirmada; lectura posterior consulta MySQL | Propietario podría ver datos anteriores si se implementase caché sin invalidación | `backend/app/publicaciones/repository.py:update_publication` actualiza por id/propietario y confirma; Catálogo invoca servicios de Publicaciones |
| Buscar/listar Catálogo | Lectura de estado comprometido en MySQL, sin copia asíncrona de Catálogo; no se promete snapshot de múltiples consultas | Una publicación recién modificada no debe permanecer obsoleta en una proyección inexistente; entre lecturas sí puede cambiar | `backend/app/catalogo/service.py:buscar_publicaciones` → `listar_publicaciones` en Publicaciones; consulta SQL directa |
| Reportar publicación | Inserción transaccional local; duplicación de reporte por usuario y publicación restringida por UNIQUE | Repetición recibe conflicto en vez de crear segundo reporte | `backend/app/administracion/repository.py:create_report`, índice UNIQUE y `transaction()` |
| Revisar reporte pendiente | Exclusión transaccional para la misma fila durante revisión; **no** atomicidad general entre reportes y visibilidad de publicaciones | Puede haber fallo parcial entre la revisión y el ocultamiento gestionado por otro contexto | `backend/app/administracion/repository.py:open_review` usa `FOR UPDATE`; ver ADR-0013 y arc42 §8.7 |
| Subir o eliminar imagen de publicación | SQL y filesystem con compensaciones, **no transacción fuerte entre ambos** | Ante crash puede quedar archivo huérfano o metadato incoherente | `backend/app/publicaciones/service.py`, `repository.py`, `image_storage.py`; reconciliación automática pendiente según S11 |

Dos verificaciones prioritarias del agente: (1) creación de publicación: SQL `INSERT` seguido de `connection.commit()` y límite de idempotencia; (2) revisión de reportes: `SELECT ... FOR UPDATE` dentro de `transaction()`. También debe comprobar el comportamiento de lectura de Catálogo.

## 3. Diseño de caché e invalidación

**Decisión S12:** no crear una caché de servidor para `publicaciones`, `precios`, `estado_publicacion`, `visible` ni reportes. La ruta normal de catálogo solicita las lecturas al servicio propietario y MySQL. No se ha identificado una medición que justifique degradar frescura ni añadir complejidad. La ausencia de caché es intencional, no una TTL sin invalidación.

| Pregunta | Respuesta vigente |
|---|---|
| Qué se cachea | Ninguna entrada mutable del dominio en caché de aplicación propuesta para S12 |
| Dónde | No existe almacén de caché de aplicación agregado por S12; MySQL y el caché interno del motor no son una proyección de aplicación |
| Cuánto tiempo | TTL no aplica: cada solicitud obtiene sus datos desde el servicio propietario |
| Quién invalida | No hay claves persistentes que invalidar; no se necesita vencimiento tras escrituras para esta estrategia |
| Cuándo reevaluar | Si EC-01 demuestra latencia insuficiente bajo medición reproducible, proponer una nueva decisión y benchmark |

**Diseño alternativo NO implementado:** cache-aside de listado por filtros, clave canónica de parámetros, TTL corto de protección y **invalidación tras confirmar** creación, edición, cambio de estado, ocultamiento o borrado; incluir índice de claves o invalidación por versión de catálogo para no dejar variantes antiguas. Ante fallo de invalidación no prometer read-your-writes: omitir caché/bypass o devolver error según operación. Las entradas privadas nunca se mezclarían con claves públicas. No agregar un Redis ficticio al C4.

## 4. Eventos, orden y entrega

No hay broker ni consumidores asíncronos productivos declarados para esta ruta: la comunicación Flutter–FastAPI es HTTP/JSON y Catálogo–Publicaciones es una llamada interna. En consecuencia, garantías `at-least-once`, `at-most-once`, particionado y DLQ **no aplican a un flujo productivo inexistente**. El taller de mensajes se evalúa **por separado**, y cualquier simulador se documentará como aislado; no se incorporará aquí como funcionalidad ya presente.

## 5. Decisión más costosa de revertir

[ADR-0022 — Mantener MySQL como fuente de verdad y evitar proyecciones asíncronas](../adr/0022-mantener-mysql-como-fuente-de-verdad-y-evitar-proyecciones-asincronas.md). La distribución de autoridad de datos, los identificadores y la integridad requieren migrar registros, consumidores y operaciones al revertirlos. Es más costoso que cambiar una política TTL. Las alternativas incluyen proyección por eventos y nuevo almacén; se explicita el plan y riesgos de reversión.
