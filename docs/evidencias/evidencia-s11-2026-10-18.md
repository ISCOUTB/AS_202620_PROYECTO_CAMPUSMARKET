# Evidencia S11 — Fallos parciales y decisión de extracción · CampusMarket

Fecha de preparación: 2026-10-18 (America/Bogota). Base inspeccionada: `master` `1582c1ff609202fa2cc4a06fa14d18b9b61bed74`. **Este documento distingue diseño propuesto de código existente.** No se declara prueba ejecutada, CI verde ni despliegue S11 sin resultados verificables.

## 1. Integración principal real y límites

La integración distribuida principal del MVP es **Flutter Web/Android → FastAPI** mediante HTTPS/HTTP JSON y multipart, con autorización Bearer para mutaciones. Recorrido representativo: `frontend/campusmarket/lib/publicaciones/publicaciones_api.dart` (`crearPublicacion`, `_request`) → `backend/app/publicaciones/router.py` (`POST /publicaciones`, `crear`) → `backend/app/publicaciones/service.py` (`crear_publicacion`) → `backend/app/publicaciones/repository.py` (`create_publication`) → MySQL. El `INSERT` y `COMMIT` son reales. El frontend tiene timeout de 20 segundos al enviar y otros 20 al consumir la respuesta; **no** hay reintento automático de esa mutación ni clave de idempotencia en la ruta inspeccionada.

Otra frontera remota es FastAPI → MySQL, y la persistencia de imágenes abarca MySQL + volumen de archivos. **Catálogo → Publicaciones es llamada interna Python**, no comunicación entre microservicios: `backend/app/catalogo/service.py` importa funciones de `backend.app.publicaciones.service`. Véase `docs/arc42/08-conceptos-transversales.md` y `docs/c4/02-contenedores.md`.

**Interpretación de «responde dos veces»:** HTTP convencional no entrega dos respuestas de aplicación a una misma solicitud; el caso relevante para idempotencia es repetición de la **solicitud/entrega** ante timeout o reintento. Se analiza esa repetición y no se afirma que el backend genere dos respuestas HTTP a un socket.

## 3. Diseño concreto de idempotencia (S11)

**Operación:** `POST /publicaciones` con usuario autenticado. **Propuesta, aún no implementada.** El cliente genera una clave aleatoria de alta entropía (p. ej. UUID v4) al iniciar el intento de creación y la conserva hasta conocer el resultado; la misma intención usa la misma clave en reenvíos, una creación nueva usa clave nueva. No se deduplica por título o precio, porque un usuario puede publicar ofertas iguales legítimamente.

**Almacenamiento propuesto:** tabla MySQL `solicitudes_idempotentes` de Publicaciones con `(propietario_id, operacion, clave)` **UNIQUE**, `payload_hash`, `estado`, `publicacion_id`, metadatos de resultado y expiración. No almacenar Bearer ni contenido sensible; emplear hash canónico del cuerpo validado. **Transacción:** dentro de la misma transacción que el `INSERT` de `publicaciones`, reservar clave, insertar publicación, guardar referencia y confirmar. La unicidad SQL coordina solicitudes concurrentes; el segundo request, tras esperar/releer el resultado de la primera transacción, devuelve el mismo recurso. Si la misma clave llega con otro hash, responder 409 sin mutar. No insertar reserva en transacción separada sin recuperación de estados intermedios. Ante crash antes de commit, rollback libera la reserva; después del commit, queda recuperable el ID. Definir semántica del código de respuesta repetida en OpenAPI (201 original o 200 replay, coherente en tests). Expiración con limpieza segura que no borre claves mientras puedan existir reintentos activos; documentar ventana de retención.

**Pruebas de aceptación pendientes:** T1 dos POST seriales misma clave+cuerpo ⇒ un ID/una fila; T2 solicitudes concurrentes misma clave ⇒ una fila; T3 misma clave+otro cuerpo ⇒ 409/sin modificación; T4 caída de respuesta después del commit ⇒ repetición recupera la misma publicación; T5 dos claves distintas ⇒ dos publicaciones legítimas; T6 aislamiento por usuario ⇒ no filtrar respuesta de otro propietario; T7 contrato OpenAPI y cliente Flutter alineados. No ejecutar estas pruebas contra producción sin consentimiento y limpieza.

**Sagas y outbox:** el flujo principal `POST /publicaciones` escribe una tabla propia en una transacción MySQL, por lo que **no necesita una saga distribuida actualmente**. Las mutaciones de imágenes sí atraviesan SQL/archivos: existe compensación parcial, pero no durabilidad ante crash. Una saga/registro persistente de tareas compensatorias se evaluaría ante una separación real de servicios o pasos autónomos que no comparten transacción. Un outbox transaccional solo procede cuando se deba publicar de forma confiable un evento junto al cambio SQL; CampusMarket no cuenta hoy con broker ni eventos de dominio garantizados. Mensajería corresponde a S12.

## 4. Decisión de extracción

[ADR-0021: mantener Catálogo en el monolito modular](../adr/0021-mantener-catalogo-en-el-monolito-modular.md). Compara extracción real, mantenimiento modular y crecimiento futuro, con criterios de carga, costo, acoplamiento, dependencia de datos y operabilidad. La alternativa **no extraer** es evaluada explícitamente.

## 5. Verificación y límites de la evidencia

- **Verificado por lectura de código:** rutas de integración; timeouts del cliente; 503 y rollback MySQL; ausencia de clave de idempotencia; llamadas internas de Catálogo y compensación de subida de imágenes.
- **No verificado mediante ejecución para esta S11:** fallos inyectados, duplicación reproducida, idempotencia implementada, regresión, hashes de CI, SHA desplegado, recuperación real de contenedores. Cada uno queda **pendiente**, no «cumple» por existir este documento.
